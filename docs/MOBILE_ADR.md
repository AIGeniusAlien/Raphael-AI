# Mobile implementation decision: shared responsive web first

Decision: retain the existing FastAPI backend,scoped cookie sessions and static web client. The connected-care page is a working mobile web client,not a parallel backend or native-app scaffold. A manifest and iOS home-screen metadata point to the same authenticated care workflow. Chromium390px viewport testing exercises real patient intake,emergency information,sharing,clinician review and revocation. iPhone Safari,physical microphones,native installation,push and App Store review have not been tested.

Do not store medical records,tokens or emergency packets in localStorage,IndexedDB or a service-worker cache. The application adds no service worker/offline PHI store. Explicit JSON export produces a local patient-controlled download; users need device protections. Default browser session cookies remain HttpOnly/SameSite; Secure requires HTTPS. A web manifest is not proof of OS installation or native/App Store readiness.

Next native step,when justified: a maintained iOS wrapper over the same API/origin with system authorization flows,platform keychain/device session binding and explicit microphone permission disclosures. Biometric unlocking must protect locally stored device credentials,not replace server authentication or record-sharing consent. Native code signing,Apple developer account,Xcode/supported build host,privacy labels,account deletion rules,medical-app review and independent security review are external prerequisites. Android follows the same backend contract. No Capacitor/React Native dependency is introduced merely to claim a native app.

Push notifications require an authorized provider and opaque event IDs; never put diagnoses or chart details on lock-screen payloads. Offline emergency summaries require a separately reviewed encrypted minimum-data store,revocation/expiration behavior and caregiver/jurisdiction rules. These are tracked requirements,not current functionality.
