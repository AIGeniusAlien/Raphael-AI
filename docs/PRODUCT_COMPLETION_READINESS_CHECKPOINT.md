## Implemented functionality

- Accessible SwiftUI organization/username/password/second-factor sign-in against the existing FastAPI authentication system. Native requests use HTTPS, a fixed configured origin, no redirects, no shared cookie/cache storage, and a private memory-only HttpOnly cookie. The server session is validated before the same cookie is handed to ephemeral WebKit. Local clear discards that context and creates a fresh isolated store for the next sign-in;the old process callback is not an authentication prerequisite. Server logout and local clear remain distinct when offline. Foreground/session checks handle expiry and revocation. No JavaScript credential injection, TLS exception or production credential is added. App-process termination still requires a new sign-in; persistent Keychain sessions are not implemented.
- Durable browser logout recovery hides data immediately, bounds requests, keeps a retry control after transport failure, and blocks account switching until remote invalidation is confirmed. A tab-local boolean intent survives reload; credentials are never placed in tab storage. Server401 is checked independently of visual hiding. A CI test that incorrectly equated hiding with completed revocation was corrected and its failure retained.
- Authenticator MFA integrated into account management, web sign-in and native sign-in. Encrypted pending TOTP secrets expire after ten minutes; activation requires current password and a valid authenticator code. Replay protection, bounded clock skew, ten hashed one-use recovery codes, account management throttling and revocation of other sessions are implemented. Lost/incorrect encryption keys fail closed. An additive MFA schema-version stamp prevents pre-MFA runtimes from silently opening the database and bypassing factors during rollback. Authenticator codes do not establish clinician licensure or verified patient identity. External password-reset delivery and enterprise MFA enforcement policies remain incomplete.
- Six practical clinician-authored paperwork workflows: care plans, medical necessity, prior authorization, insurance appeals, structured forms and coding-review preparation. Fields are bounded, unauthorized chart/transcript source IDs are rejected, missing fields are explicit, and source snapshots survive edits. Existing optimistic version checks, immutable approvals, audit events and explicit patient publication apply. All six have actual API lifecycle tests; the care-plan flow also has real browser acceptance. These are preparations, not automated coding, clinical synthesis, payer submissions or signed legal forms.
- Evidence versions stage before publication. An interrupted new-version batch preserves the old active version; retries complete the staged document without deleting history. Source-date rollback is refused. Explicit source withdrawal preserves vectors and provenance while excluding retrieval/citations; generic reingestion cannot silently readmit it. Read-only refresh planning reports updates separately from retractions. This does not establish automatic retraction surveillance or add specialty knowledge.
- Authenticated-encryption synthetic SQLite backups and restore to a new private file. SQLite snapshots are consistent, integrity/foreign-key/schema checked, and existing files are never overwritten. Wrong keys and tampering are rejected before restoring. The bounded CLI supports databases up to 16 MiB. This encrypts backup artifacts, not the live database, and is not a production disaster-recovery service.
- A reproducible bounded real HTTP/SQLite concurrency probe, expanded source-security scan, and a Chromium MFA/recovery-to-approved-care-plan-to-patient journey. The existing design and assets are preserved. Desktop, tablet, mobile and enlarged-text captures test overflow; desktop, tablet, mobile and enlarged-text images were inspected. A reproduced 320px account overflow (363px content width) was fixed by wrapping private MFA material; the actual browser regression passed without capturing private codes.
